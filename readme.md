【项目汇报】轻量级 2D Web 虚拟桌游平台（VTT）开发方案概要

一、 项目目标
打造一个自建自托管、免规则判定的纯沙盒 2D Web 虚拟桌面。核心解决朋友无需安装任何客户端、使用老旧低配手机通过浏览器即可流畅联机的痛点。首期承载 200+ 棋子的双盲军棋，底层设计为通用架构，后续无缝兼容跑团（TRPG）、卡牌及战棋类桌游。

二、 核心功能特性

多端触控适配： 支持单指平移、双指缩放（Pan & Zoom），采用“点击选中 + 点击落子”的两段式操作与网格自动吸附，解决小屏误触与手指遮挡问题。

双盲与自由沙盒： 客户端依据玩家阵营本地控制正反面渲染，支持棋子自由翻面、旋转、移动，剥离复杂胜负判定逻辑，专注还原实体桌面操作。

跑团与桌游工具链： 内置轻量多面骰系统（D4~D100 及加值运算），纯 CSS 硬件加速渲染，配有实时事件日志流。

存档与生态复用：

房间状态支持本地 JSON 导入导出与服务端自动防抖备份；

配套提供 Tabletop Simulator（TTS）存档转换工具，可直接将 Steam 创意工坊的现成 3D 模组一键转换为 2D Web 盘面，零成本复用海量桌游资产。

三、 极限低配双端性能优化方案
针对极弱移动设备与低配置自建服务器做了针对性工程减负：

手机端（防卡顿/防崩溃）： 弃用臃肿 DOM 与高负载 3D 引擎，采用原生双层 Canvas（底图静态冷冻 + 顶层按需重绘）；棋子贴图采用大图合辑（Atlas/WebP）与分辨率封顶限制，彻底杜绝显存溢出与掉帧发热。

服务端（压榨极低算力）： 摒弃重型 Socket.io，改用极简原生 WebSocket 纯中继架构；仅同步微型增量操作包（Delta Sync），无常驻大计算；磁盘落盘设 5 秒防抖节流，常驻内存控制在 30MB 以内，CPU 日常接近 0 占用。

## 坐标模型（重要）

**没有网格，地图无限大。**

- 棋子位置是**任意浮点世界坐标**（表示棋子中心），可正可负，服务端不钳制范围。
- 落子/拖拽**不吸附、不取整** —— 拖到哪就落在哪，精确到屏幕反解出的小数。
- 平移没有边界，可以一直拖下去。
- **每枚棋子有自己的世界尺寸**（`w`/`h`）。真实资产里 `scaleX` 从 0.6 到 15
  （差 25 倍），底图板块还是 1.5:1 的长方形 —— 所以早已不是早期 demo
  那个全局固定的 `PIECE = 64`。命中测试也按各自矩形算。

坐标换算分两段：

```
构建期（tools/build_assets.py，输出 TTS 原始符号）:
  原始 x = posX * 32       原始 y = posZ * 32
  世界 r = 180 - rotY      （推导见 tools/build_assets.py 文件头，有硬证据）
  f = 1 当 |rotZ| ≈ 180    （平面棋子被翻成背面朝上）
  世界边长 = 64 * scale    高度按图片宽高比换算

运行期（public/app.js，可切换的显示映射）:
  显示 x = 原始 x * ±1     显示 y = 原始 y * ±1
```

`r` 用 `180 - rotY` 而不是 `-rotY`：本模组 762 枚棋子的 `rotY` 都 ≈180，
代入得 `r = 0`（原图正着画）。写成 `-rotY` 时 `-180` 与 `+180` 同余，
等于又转了一次 180°，整个盘面的文字倒立 —— 这是实际发生过的事故。

轴符号（`±1`）**推不唯一**，做成设置项由使用者目视选定，见「位置映射」一节。

> 早期版本是 12×20 网格 + 吸附，已按需求移除。

## 协议

```
C→S  {t:"join"}                      握手信息走 URL query（room / name）
S→C  {t:"init", seq, scene, label, pieces:[{id,x,y,r,f,w,h,img,bimg,z,lk,si,st,ds,v}]}
C→S  {t:"op", op}
S→C  {t:"op", seq, by, op}           广播给全房间，含发送者
S→C  {t:"peer", n}                   在线人数
```

`pieces` 里每枚棋子带自己的 `w`/`h`（世界尺寸）和 `img`/`bimg`
（正面/背面贴图 id）。`f` 决定画哪一张。
`lk` 是冻结标记，`si` 是当前形态下标，`st` 是形态数组
（`st[0]` 即 TTS 存档里的原始形态，单形态棋子的 `st` 为 `null`）。
`ds` 是骰子面数（0 = 非骰子），`v` 是骰子当前点数。

op 全部是**绝对赋值**，因此幂等：

```
{k:"move",  list:[{id,x,y}, ...]}   浮点世界坐标（棋子中心），不是像素
{k:"flip",  id, f}                  f: 0|1
{k:"rot",   id, r}                  r 是**任意角度**，保留两位小数
{k:"lock",  id, lk}                 lk: 0|1（冻结）
{k:"state", id, si}                 切形态，回包含新的 img/bimg/w/h
{k:"clone", id, x?, y?}             回包含完整的新棋子 piece
{k:"del",   id}
{k:"dice",  ds, x, y}               加骰子（ds ∈ 2/4/6/10/12）
{k:"roll",  ids:[...]}              掷骰，回包含每颗的点数与新 z
```

`move` 统一走**批量形式**（单枚移动就是长度为 1 的批量），
省掉「单枚 / 多枚」两套代码路径，多选拖拽天然复用同一条链路。

`clone` / `dice` 的 id **由服务端分配**（`c<n>_<源id>` / `d<n>_<面数>`）：
让客户端各自取名会在并发时撞 id。

**批量 op 里只要夹了一枚冻结的棋子就整批拒绝**（`move` 和 `roll` 都是）。
所以客户端在 `onDragEnd` / 掷骰前先剔除冻结项 ——
否则一次「全掷」会因为夹了一颗冻结骰子而整批不动，
用户看到的是「点了没反应」，很难联想到是那颗冻着的骰子。

`roll` 的点数**只能由服务端给**。这不是洁癖：客户端各摇各的，
同一张桌上的两个人会看到不同点数，那就不是骰子了。

`x`/`y` 必须是 JSON number 且有限。**不能用宽松的 `Number(v)` 校验**：
`JSON.stringify({x:NaN})` 产出的是 `null`，而 `Number(null) === 0`，
一个 NaN 坐标会被静默当成 `(0,0)` 收下（`Number('')`、`Number([])` 同理）。

服务端的回包会在 `list` 各项里**补上权威的 `z`**（层叠序，见下文）。

**网络上来回的坐标都是 TTS 原始坐标**，轴符号翻转在前端做
（见「位置映射」一节）。服务端不关心显示约定。

**关于 op 回显的挑选**：广播时直接把 `applyOp` 的返回值透传，
**不要在转发处手写字段白名单** —— 那样每加一个 op 就要记得同步一次，
漏掉就静默丢字段。这个坑踩过两次（`move.list` 和 `clone.piece`）。

**为什么 seq 不能省**：op 幂等让本地可以先乐观应用、服务端回显重复应用无害；
但「幂等」不等于「有序」——若让客户端各自编号，两个客户端并发操作时
两端应用顺序会不同，画面就撕裂了。服务端串行分配 seq 后广播，
全序是白送的，于是这一版完全不需要 OT / CRDT / 回滚。

## 存档 / 读档

**只输出 base64 文本，供复制粘贴，不写文件。**

```
GET  /api/save?room=X    -> { count, bytes, label, scene, data:"<base64>" }
POST /api/load           <- { room, data:"<base64>" }
GET  /api/scenes         -> 场景目录
POST /api/scene          <- { room, slug }
```

走 HTTP 而不是 WebSocket：导出/导入是一问一答的请求，
而且 base64 到 72KB，塞进 WS 会顶到 `maxPayload`。

存档不是把棋子对象直接 `JSON.stringify`，而是做了一层紧凑编码：

- **列式数组**代替对象数组，省掉 778 份重复键名
- **贴图字典**去重 —— 被 120 枚棋子复用的图只出现一次
- 778 枚棋子 → **67.8KB 紧凑文本 / 90.3KB base64**
  （接入 `States` 前是 54KB / 72KB；把角度精度从一位小数
  修正为两位小数又涨了约 0.2KB —— 那点体积换的是无损往返）

**id 必须在往返中保持不变。** 早期实现每次导入按位置重新生成
`p0..pN`，而场景用的是 `t012` 风格 —— 结果「导出再导入」之后 id 全变，
客户端已有的多选集合、层叠关系、进行中的 op 引用全部悬空。
现在 id 存在紧凑格式的 `ids` 表里（场景 id 规整时可省略）。

行结构是 `[x,y,rot,f,w,h,ai,bi,z,lk,si,ds,v]`（13 项，下标 0..12）。
**注意 `si` 在 10 不是 11** —— 早期写成读 `r[11]`，恒为 `undefined`，
于是 `si` 永远解析成 0：形态选择被静默重置，而且「下标越界」
这条校验也永不触发。两个症状都不报错，属于最难发现的那类。

**角度 `r` 的精度是一个真踩过的坑**，三处必须一致：

| 位置 | 正确精度 | 错误写法的后果 |
|---|---|---|
| `build_assets.py` | `round(..., 2)` | — |
| `codec.encode` / `decode` | 两位小数 | 用 `r1` 把 `0.27` 变 `0.3`；用 `Math.round` 直接抹平 |
| `room.js` / `app.js` 的 `rot` op | 两位小数 | 同上 |

场景里 **7796 枚棋子有 596 枚（7.6%）的朝向是 `0.27`、`359.94` 这类小数**
（`180 - rotY` 换算的余数）。早期 `encode` 写一位小数、`decode` 却
`Math.round` 取整，于是「导出再导入」每轮都在丢精度 ——
不报错、但不可逆（存档字节数会随之下漂，实测 92300 → 91900）。

还有一个更隐蔽的浮点问题：**不能写成 `((r % 360) + 360) % 360`**。
`0.27` 先 `+360` 变 `360.27`，再取模得到 `0.2699999999999818`。
结果是同一枚棋子在服务端与客户端算出的 `r` **不相等**，
虽然四舍五入到两位小数后肉眼无差，但会让「往返是否稳定」的
判断产生假阴性。正确写法是先归一到非负、**再**取整。

形态数组（`st`）**稀疏存放**：778 枚里只有 59 枚有多形态，
按行下标写成 `{行号: [[img,bimg,w,h], ...]}`，只有存在时才落这个键。
全量存会让体积翻倍且 92% 是冗余。

导入校验从严：存档是用户手动粘贴的，宁可整份拒绝也不要塞一半坏数据进房间
（房间状态是所有客户端的一致性基准，脏数据会传染）。
版本号、行长度、数值有限性、贴图下标、形态格式与下标、id 重复都会拒绝。
较早的 9 列存档仍可正常导入（缺列按默认值补）。

> 导入存档后 `scene` 字段会置空 —— 那是正确语义：
> 盘面已不等于任何场景快照，自然不该再挂着原场景名。

## 大坐标下的渲染精度

无限地图意味着世界坐标可以很大。**不能把世界坐标直接交给 canvas**：
部分实现内部先降到 float32（约 7 位有效数字），于是
`float32(1e7 + 0.5) === 1e7` —— 小数部分被直接丢掉，出现可见抖动。

所以 `drawFg` 只做 `scale(s)`、**不做 translate**，绘制坐标统一写成
`世界坐标 - view.ox`（`ox = -tx/s`，即屏幕左上角对应的世界坐标）。
这样无论棋盘挪到多远，交给 canvas 的永远是屏幕级的小数值。
实测世界坐标在 1e7 量级时，传给 `drawImage` 的偏移仍是 74~397。

> 有就是拖拽，没有就是点击。

## 棋子菜单与形态

菜单项与实现要点：

| 项 | 行为 |
|---|---|
| 翻面 | `flip`，切换正/背面贴图 |
| 旋转 | `rot`，**滑杆任意角度**（0..359）+ 0/90/180/270 预设 |
| 形态 | `state`，**单选列表**直接点目标形态 |
| 固定（冻结） | `lock`，冻结后不可拖动/翻面/旋转/切形态/掷骰 |
| 克隆 | `clone`，原样复制并偏移一点，压最上层 |
| 删除 | `del`，**唯一不可逆操作**，有二次确认 |

菜单项有三种类型（见 `menu.js`）：普通项、`radio` 单选列表、`slider` 滑杆。

**旋转滑杆为什么用 `change` 而不是 `input` 提交**：`input` 在拖动过程中
会持续触发，一次从 0 拖到 359 就是几百个 op，服务端 seq 会被灌爆。
现在拖动只更新显示的数字，松手（`change`）才发一个 op。
滑杆传的是**目标绝对角度**，不是增量，所以多选时所有项都转到同一角度。

**形态为什么改成单选**：原来是「点一次切下一个」，形态多的时候
（本模组有 9 形态的对象）要连点到目标，而且看不见全貌。
现在把每个形态列成一行直接点，当前项高亮。

**形态（TTS 的 States）怎么表示的**：TTS 存档里
**顶层对象就是当前形态，`States` 字典里是其余形态**。
本模组 59 个对象有多形态（2/4/6/9 种），每个形态有自己的图片和尺寸。

两个坑：

1. 形态自带的 `Transform` 坐标是**残留数据** —— TTS 切形态时位置不变，
   所以只取图片和尺寸，位置一律沿用顶层。
2. 形态是**稀疏**的：778 枚里只有 59 枚有多形态。存档里用 `st` 表
   按下标稀疏存放，全量存会让体积翻倍且 92% 是冗余。

**冻结在服务端拦截** `move`/`flip`/`rot`/`state`/`roll`：前端不拖只是
「不去做」，服务端才是权威。但 `lock` 本身必须能作用于已冻结的棋子，
否则一旦冻上就再也解不开了。

冻结的棋子在画布上画**蓝色虚线框**，与橙色的实线选中框区分开。

## 骰子

`d2 / d4 / d6 / d10 / d12`，工具栏「加骰」放在当前视图中心，
「掷骰」掷选中的骰子（没选中就掷场上全部；场上一颗都没有就给一颗 d6）。

**骰子就是棋子**，只多两个字段：`ds`（面数，0 = 非骰子）、`v`（点数）。
这样它白拿棋子已有的全部能力 —— 同步、层叠序、拖动、克隆、删除、
冻结、存档往返，一行新代码都不用写。两个新 op：

```
{k:"dice", ds, x, y}      加一颗，服务端分配 id 并回含完整 piece
{k:"roll", ids:[...]}     掷，回含每颗的点数与新 z
```

**点数必须由服务端随机**。让客户端各摇各的，同一张桌上的两个人
会看到不同点数 —— 那就不是骰子了。客户端只负责把动画演到那个结果上：
本地先演起来（否则网络慢时有明显迟滞），点数揭晓的瞬间
就是服务端回包到达时，而**结果始终以服务端为准**。

拟真动画，几处刻意的细节：

- **落影随抛起高度缩小变淡** —— 高度感几乎全靠它，没有影子的
  骰子看起来就是在原地打转
- **单次抛物 + 落地压缩回弹**，而不是匀速转然后瞬间弹出答案
- 骰身画一层偏移的深色表示**厚度**，不是一张平贴纸
- 每颗骰子有固定相位（由 id 哈希），同时掷出也不会整齐划一地转
- 滚动中点数**快速闪烁**（用进度做伪随机，保证同一帧内稳定），停下才揭晓

d6 用点数孔（比数字更像实物），其余面数印数字（更易读）。

**动画续帧是有条件退出**的：只在真有骰子在滚时排下一帧，
不做常驻 rAF（那会让手机一直保持唤醒）。
注意动画的推进与清理必须放在**帧首统一做**，不能写在「画某颗骰子」
的分支里 —— 那条路径前面有视口裁剪，把骰子拖出屏幕后清理就永不执行，
到期条目一直留着、`pendingAnim` 永远为真，于是变成常驻 rAF 死循环。
这类 bug 在画面上完全看不出来，只费电。

## 多选与层叠序

**多选**有三种途径：框选、Shift+点击（桌面）、`Ctrl/Cmd+A` 全选。
拖动已选中的任意一员，整组一起移动。

整组移动的实现：`board.js` 只上报一次拖拽产生的**世界位移量**，
`app.js` 把这个位移加到所有选中棋子上，最后合成**一个批量 op** 发出。
所以拖 100 枚棋子和拖 1 枚，网络开销完全一样。

**层叠序（z）**：每个被移动过的棋子会拿到一个递增的 `z`，
绘制时按 `z` 升序、命中测试时取 `z` 最大的，
于是**最后放的在最上面**，重叠时点得到的就是它。

`z` **必须由服务端分配**。如果让客户端自己发，
两个客户端并发移动时对「谁更晚」的判断会不一致，
重叠时的上下关系就会各画各的 —— 这是和 `seq` 同一类的全序问题。

翻面/旋转**不**改变 `z`：只有「放下」才改变层叠关系。

批量 op 是**全有或全无**的：只要有一项的 id 不存在或坐标非法，
整批拒绝、不分配 seq。否则会出现「一半棋子动了、一半没动」的撕裂状态。

### 拖动会连带被覆盖的棋子

拖一枚棋子时，**压在它上面的棋子跟着一起走**（需求如此）：
判定是「矩形相交 + `z` 更大」，且取**传递闭包** ——
A 压 B、B 压 C 时拖 C，A、B 都跟着走，否则上面的牌堆会散开。

这里有个必要的配套：**渗选**。`pick()` 只返回最上面那枚，
所以底层棋子原本**永远选不中**，「拖底下的棋子」根本无从触发。
现在同一位置重复点击会依次选到下面一层（C→B→A→C 循环），
`onDragStart` 里若起点处已有选中项就**沿用当前选择**、
不替换成最上面那枚 —— 否则渗选刚选好底层，一拖就被顶掉。

冻结的棋子**完全不参与拖动**（视作钉在桌上）。注意不能只在最后
剔出批量：那样 `onDragMove` 仍会改它们的坐标，屏幕上跟着走、
服务端却从不确认，表现为「拖完弹回去」。

## 位置映射（可切换）

TTS 存档给的是 `(posX, posZ)`，映射到 2D 画布有 4 种轴符号组合。
**纯数学推不唯一** —— 存档缩略图是透视视角，信噪比太低
（实测最好的组合相关性只有 0.08），所以做成设置项由使用者目视选定。

关键性质：这个映射**只翻符号、是自逆的**（应用两次 = 恒等）。
因此「显示坐标 → 原始坐标」和「原始坐标 → 显示坐标」是同一个函数。

约定：

- 服务端与磁盘**永远只存 TTS 原始坐标**
- 客户端内存里**永远是显示坐标**
- `init` / 远端 op 进来时 原始→显示；发出去的 op 显示→原始

这样切换映射档位不会污染数据，导出存档也永远是一致的原始坐标。
构建脚本也因此不再把翻转烘进资产 —— 换映射无需重跑管线、无需重启。

## 性能相关的几个刻意选择

- **双层 Canvas**：`bg` 只在视变换变化时重绘（无限地图上它只画一个原点准星），
  `fg` 按需重绘。
- **无常驻 rAF 循环**：输入事件标脏 + `requestAnimationFrame` 一次，画完即停。
  空转的 rAF 会让手机持续保持唤醒。
- **分辨率封顶**：`canvas.width = cssW * min(devicePixelRatio, cap)`，
  小屏（≤500px）cap = 1.5，其余 2。
- **视口裁剪**：只画落在屏幕范围内的棋子。无限地图理论上可以放任意多棋子，
  这一步保证绘制成本只跟"看得见的数量"有关，与总量无关。
- **大坐标用屏幕原点抵消**：见上文「大坐标下的渲染精度」。
- **拖拽期间不发 op**：松手才发一条批量 `move`。整组多选也只发一条。
- **写盘原子性**：先写 `.tmp` 再 `rename`，避免进程中断留下半个 JSON。

### 贴图显存（接入真实资产后的核心问题）

1003 张贴图全部解码成 RGBA 约 **290MB**，老手机必崩。所以做了两层控制。

**第一层：LOD —— 屏幕长边 < 18px 就不加载贴图，改画色块。**

这是「缩到全场景不爆显存」的关键闸门。全场景适配时 778 枚棋子同时在屏幕上，
若每枚都要真贴图，LRU 一张也淘汰不掉（全都「可见」），
瞬间就是 778 × 192×192×4B ≈ **114MB**。
实测开了 LOD 后全场景视图的贴图请求数是 **0**，762 枚走色块、
只有 16 张大板块加载真图。

**第二层：按字节预算的 LRU，而不是按张数。**

这一条是踩坑踩出来的。最初限「512 张」，实测峰值 **112.6MB**，
因为：

| 类型 | 解码后 |
|---|---|
| 小棋子贴图 192×192 | ≈ 147KB |
| 地图板块 1024×680 | ≈ **2.8MB**（一张顶 19 张小图） |

按张数计时，11 张离屏底图（30MB）会因为「张数没超」而永远赖在缓存里。
改成按解码字节数限量、底图单独限 3 张后，真实最坏视口
（s≈0.5，同屏 458 枚超 LOD、唯一贴图 384 张）实测峰值
**112.6MB → 65.1MB**。

> 顺带修掉一个计数泄漏：淘汰一张**还在加载中**的贴图时，
> 只把 `onload` 置空就删记录，`pending` 永远收不回来 ——
> 曾经一路涨到 5243，加载进度完全失真。

**贴图请求不再抖动**：修好容量后，横扫全图各缩放档的新增请求从
**15323 次降到 539 次**（唯一贴图仅 1003 张）。抖动比多占内存更糟 ——
它会让低端机反复解码，帧率崩得比内存更早。

## 已知限制

- **没有双盲**：README 说的「客户端按阵营控制正反面」尚未实现，
  现在的 `flip` 是全局可见的。**贴图模型已经支持正反面**，
  但服务端仍会把两面的贴图 id 都发给所有客户端 ——
  改个前端就能看穿。真正双盲需要服务端按连接裁剪下发，
  与当前「纯中继不做判定」的架构有冲突，是独立的设计决策。
- **`States` 的缺失资源**：59 个对象的多形态已接入，但其中 25 个形态的
  贴图在资产包里找不到（TTS 存档引用的是 Workshop 上的远端资源），
  这些形态回落到 `white.webp` 白图。形态数量与切换逻辑本身是对的。
- **3D 对象已跳过**：2 个 `Custom_Assetbundle`、1 个 `Custom_Model`、
  10 个 `HandTrigger`、2 个 `FogOfWarTrigger`、6 个 `Die_10`、3 个 `Custom_PDF`。
  降维不可逆，且与本版目标无关。
- **重叠点选靠「重复点击」而非穿透菜单**：同一处连点会在重叠的棋子间
  循环（C→B→A→C）。够用，但没有做「列出该处所有棋子让你挑」的浮层。
- **克隆不递归**：多选时只克隆第一枚（一次冒出一堆容易失控）。
- **骰子没有历史记录**：只看得到当前点数，没有「谁在哪轮掷了什么」的日志。
  要做的话得在服务端留一份 append-only 事件流。
- **骰子只区分面数，不区分材质/大小**：`d6` 就一种画法，
  尺寸按面数固定（44~56）。桌游里常见的「不同颜色的骰子」还没做。
- **形态的 25 个缺失贴图回落到白图**：见上。
- **单条消息上限 1MB**：一批 778 枚棋子约 26KB，够用；
  若将来棋子数涨到几万，批量 op 会顶到 `ws` 的 `maxPayload`
  （超限时连接会以 1009 断开，而不是被静默丢弃）。
- **无限地图没有边界保护**：理论上可以把棋子拖到 1e15 这种量级，
  浮点精度会开始明显退化。目前不做限制。
- **无鉴权、无房间管理**：知道 room 名即可进入，任何人可发任何 op。
  `/api/load` 也是任何人可调用 —— 局域网可信场景的前提。
- **无断线增量补发**：重连直接拉全量快照（778 枚约 82KB，可接受）。
- **删除不可撤销**：有二次确认，但没有 undo 栈。
- `data/` 未做房间回收，长期运行会累积快照文件。
